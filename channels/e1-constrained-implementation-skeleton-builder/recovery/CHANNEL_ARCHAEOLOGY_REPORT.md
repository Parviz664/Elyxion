## Archaeological question

“Kем E1 на самом деле был, как он стал тем, кем является, и где заканчивается его власть?”

## Finding 1 — E1 has two major eras

### Era A — implementation-thinking / execution-draft
Versions:
v1.0, v1.1[missing], v1.2, v1.3.

Core:
locked upstream context -> detailed constrained implementation plan.

Characteristic outputs:
steps, metrics/exit, rollback, dependency graphs, execution drafts, D1/E2 handoff.

### Era B — constrained skeleton authority
Versions:
v1.4, v1.5, v1.6.

Core:
immutable E0 bind -> structural skeleton/fences/evidence hooks -> E2, weak E3 visibility.

Characteristic prohibitions:
no build plan, no readiness, no runtime, no human tasks, no hidden downstream authority.

These eras MUST NOT be merged.

## Finding 2 — v1.4 is the real architectural pivot

The role shift is explicit, not inferred.

v1.4 itself declares breaking changes:
execution draft leaves E1;
E3 gets build planning;
E2 becomes engine-contract translation;
E1 becomes E0-handle-only skeleton builder;
proof hooks replace metric-style planning in E1.

## Finding 3 — the technical name lagged behind the role

v1.4 already acts like a skeleton builder but still carries technical ID:
E1_CONSTRAINED_IMPLEMENTATION_THINKING_ENGINE.

v1.5 later changes the technical ID to:
E1_CONSTRAINED_IMPLEMENTATION_SKELETON_BUILDER.

Therefore name and function did not change at exactly the same version.

## Finding 4 — no-inference evolved in placement

v1.3:
E1 directly requires registry+seal.

v1.4+:
registry+seal verification is upstream in E0; E1 consumes only the locked handle and must not become a second E0.

The no-inference principle survives, but the interface changes.

## Finding 5 — D1 relationship changed

v1.2/v1.3:
E1 authors psycho-operational touchpoint annotations and hands execution drafts to D1.

v1.4:
D1 touchpoints are explicitly NOT authored here; D1 receives separate seeds/guards and may only optionally consume E1 skeleton.

## Finding 6 — E3 relationship changed again by v1.6

v1.4:
parallel/optional handoff to E3 build plan is explicit.

v1.6:
E3 visibility is deliberately weak.

This is further role purification:
E1 must not hide build authority in a “handoff”.

This distinction is foundational for the recovery.
